# ArcFort Weld 网站生态运行闭环

本文件是跨系统交接图。各环节的具体规则仍由 `AGENTS.md`、`docs/CODEX_GOAL.md`、
`docs/CONTENT_RULES.md`、`docs/QA_CHECKLIST.md` 和相应技能、操作记录拥有。
不要用本图代替产品证据或外部服务的实际验收。

## 一条完整的买家路径

`已核实资料 → 规范产品记录 → 可发布页面 → 可抓取入口 → 带产品信息的 RFQ →
销售与买家收件 → 有效询价归因 → 资料与页面改进`

| 环节           | 权威输入与检查                                                                                     | 通过后交给                     | 失败时处理                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------- |
| 公司与产品事实 | `lib/content/site.ts`、公司声明、产品 CSV、技术/适配/图片证据登记；运行对应数据和图片校验          | 产品页面与目录                 | 保留待确认或冲突状态；向原始资料持有人索取准确证据，不从相似型号推断                               |
| 页面发布       | 路由、图片权益、元数据、结构化数据、内链和 RFQ 上下文；执行 `docs/QA_CHECKLIST.md` 与 `release-qa` | GitHub PR、CI 与 Vercel        | 修权威源，再重新生成和测试；不通过删 URL、降证据门槛或改预算让检查变绿                             |
| 搜索发现       | 生产 sitemap、robots、canonical、跳转及首页可达性；`seo:audit:live`                                | Google/Bing 原生检查与搜索基线 | 先取得原始 URL、最后抓取日期和 Google 选定 canonical；按 `docs/search-indexing-submission.md` 处理 |
| 买家询价       | 产品 SKU/型号、数量、国家和可用图片/图纸；客户端与服务器双重校验、BotID、限流、附件和幂等          | 邮件服务与销售                 | 用合成数据本地复现；保护原输入、询价编号和备用邮箱/WhatsApp，不自动重投                            |
| 交付与销售     | 服务商接受、销售收件、买家确认收件、附件可用性分别记录                                             | 真实销售跟进                   | 用同一询价编号查两端邮箱；未见收件时保持“未证实”，排查发信域、退信和服务商日志                     |
| 效果衡量       | GA4 经同意的事件、GSC 原始查询/页面数据、有效询价                                                  | 内容与产品证据优先级           | 不以按钮点击或工具“就绪”代替成交线索；缺数据时标记未知，不补造趋势                                 |
| 生产监测       | 每 6 小时 `production-health.yml`、失败 issue、部署后 `health:production`                          | 故障定位与回归                 | 记录失败 URL/域名/步骤；修可复现的根因，重新跑相关测试与完整发布门槛                               |

核心发信认证的 DKIM、SPF 或 MAIL FROM MX 若在两个 DNS 提供方都无法核实，
巡检必须失败，不能把“未查到”当作“正常”。DMARC 当前缺失仍单独报告为警告；
添加记录需要独立的 DNS 权限与核验。

RFQ 的“准备好供销售审核”只表示买家提供了可继续核对的数量、目的地和产品线索，
不表示尺寸、适配或价格已经由 ArcFort Weld 确认。泛泛提及型号、照片或请求 MOQ
不算已提供的具体依据。

RFQ 的邮件服务商接受状态只证明提交被服务商受理；销售邮箱和买家邮箱的实际收件
必须用同一询价编号分别核对。自动提交失败时，买家资料只留在页面内供手动复制，
备用邮箱和 WhatsApp 链接不得携带买家姓名、邮箱或询价内容。

## 每次变更的处理顺序

1. 确认受影响的买家路径、准确 URL/SKU、权威数据源和现有生产证据。
2. 先复现错误；把“代码缺陷”“资料未确认”“外部账户不可读”分开记录。
3. 在一个组件或产品系列范围内修复，并运行与改动表面匹配的测试。
4. 对确切差异做 `release-qa`，按 `AGENTS.md` 的目标和授权边界发布。
5. 等候 PR CI 与 Vercel 正式部署结果，再运行生产只读巡检；有交互改动时核对线上浏览器行为。
6. 把只读检查、真实收件、搜索收录和统计事件分别写回各自证据记录，不把一种成功当成另一种成功。

生产验证日期与未证实状态保存在 `docs/operations/acquisition-production-evidence.json`；
生成报告为 `docs/acquisition-readiness-report.md` 和 `docs/goal-progress-report.md`。
更新清单时只推进本次确实核对的字段，并重新生成两份报告。
