## 本批完成的系统改进

本批加强现有 `seo:audit:live`，由同一个检查入口用于本地构建、CI 和既有每 6 小时生产
巡检。未新增定时任务、付费服务、统计账户、数据库或第三方依赖。

| 环节         | 之前的检查缺口                                                         | 本批检查                                                             |
| ------------ | ---------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 首页到内容   | 页面只要出现在全站链接集合中就可能通过；相互链接的孤立页面组仍可能漏过 | 从首页实际遍历可抓取 HTML 链接，识别孤立页和不可达页面组             |
| 可抓取入口   | 查询参数被去掉，nofollow 和脚本文本可能被当成有效入口                  | 保留查询参数；尊重链接和页面 nofollow；排除脚本、注释、惰性 template |
| 分类到产品   | 主要验证少数重点页面，未逐一验证全部产品的分类关系                     | 每个活动产品要求分类正文直达产品、产品正文回到所属分类               |
| 产品到询价   | 询价按钮存在不代表正确产品信息被携带                                   | 检查规范 RFQ 目的地与完整、唯一的 SKU 字段                           |
| 备用联系入口 | 通用邮箱/WhatsApp 入口不能证明买家能带着型号联系销售                   | 检查中央配置指定的邮箱和 WhatsApp 目标，以及两种预填内容中的 SKU     |
| 防止检查失效 | 一次性人工核对无法防止以后新增页面出现同类问题                         | 新增反例测试并接入 CI；旧生产巡检自动复用增强后的审计                |

这些检查只解析公共页面并执行既有 GET/HEAD 请求，不点击联系入口、不发送邮件或询价，
也不把可达性等同于 Google 收录。图遍历仅使用直接 200、可索引、自规范的 HTML 页面，
下载文件继续由原有文件检查覆盖。链接深度作为观察值报告，没有虚构“Google 必须两层”的规则。

- 生产构建、完整 typecheck、lint、既有重试测试、SEO 内容/链接/图片/摘要和性能检查通过。

## 日常操作

修改产品/页面后，在相应数据和证据检查之外，执行：

```bash
npm run test:buyer-journey-audit
npm run build
npm run typecheck
npm run lint
npm run seo:audit
npm run seo:links
npm run seo:images
npm run seo:snippets
npm run performance:budget
```

CI 会启动同一生产构建并执行完整 HTTP 审计。发布后运行 `npm run health:production`，
查看其中的页面可达性、产品路径、RFQ 就绪、邮件域和安全检查。该命令默认不发送询价。
不得为让检查变绿而删掉故障 URL、放宽 SKU 匹配或关闭证据门槛。

出现错误时，先记录受影响 URL/SKU 和失败环节，再修对应源文件并重跑相关检查。GSC 问题
使用原始 URL 及最后抓取时间关联当前链路；公开技术检查无法替代 Google 的 URL 检查。

回滚本批仅需回退审计脚本、测试、package script 与 CI 测试步骤，不涉及数据库、产品源
或公共 URL。产品内容完善另按实际资料形成小批次，避免一次混入未核实型号。
